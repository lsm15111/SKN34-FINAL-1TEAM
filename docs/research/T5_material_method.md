## 0. 한눈에 보기 — 핵심 발견 10개

1. **도배 옵션의 시공 차이는 폭·이음·초배 세 가지로 갈린다.** 합지(소폭 530mm / 광폭 930mm)는 겹침 시공이고, 기존 합지 위에 덧방하면 철거·퍼티·초배를 생략할 수 있다. 실크(1,060mm)는 맞댐 시공이며 기존 벽지 철거, 퍼티, 부직포 띄움 초배와 운용지가 필요하다 [S08][S30][S36]. 이 차이가 견적 항목, 일정, 하자 위험을 거의 다 결정한다.
2. **롤 규격(LX 공식)**: 실크(베스띠·디아망)는 106cm×15.6m, 광폭 합지(휘앙세93)는 93cm×17.75m로, 둘 다 롤당 약 16.5㎡(약 5평)다. 수입 벽지는 롤당 약 5㎡에 그친다. 뮤럴은 3m×2.4m 주문생산이다 [S05][S16][S18][S09][S17].
3. **LX 공식 공정표에서 쓸 만한 대기시간·순서 규칙**: 퍼티 후 도배까지 2일, 마루는 도배 전, 장판은 도배 후, 전기는 1차(배선, 목공과 병행)와 2차(조명·스위치, 마지막)로 나뉜다. 1일 1공정으로 기본 공사는 평일 약 16일, 전체 20~30일이다 [S11]. 결정론적 일정 엔진의 의존성(DAG) 뼈대로 바로 쓸 수 있다.
4. **목공 옵션은 '추가로 끌고 오는 공정'이 핵심이다.** 무몰딩은 기존 몰딩 철거와 벽·천장 평탄화(석고 덧방)가 필수다. 마이너스 몰딩은 천장 덧방에 약 10mm 이격이 필요하고 비용이 일반 몰딩의 2배 이상이다. 포켓 슬라이딩은 목공 선행이 필요하다 [S06][S07]. 구축 콘크리트·조적벽은 목공 없이 무몰딩을 하면 품질이 떨어진다 [S06].
5. **천장 평탄화**: 우물천장 평탄화는 40~50만 원(도배 별도)에 목수 2명이 하루 걸린다. 등박스만 있으면 비용이 절반 이하다. 간접조명은 우물 한 변이 3.8m를 넘으면 10만 원이 추가된다. 덧대기만 하면 천장이 처지고, 띄움 도배를 해야 조명 아래에서 석고 이음이 드러나지 않는다 [S42]. 노후 석고는 철거 중 탈락할 수 있고 스프링클러·감지기 배선을 동시에 계획해야 한다 [S10].
6. **방문·문선 비용은 출처 간 편차가 크다(상충).** 개인 후기 기준 9mm 문선 20~30만, 무문선 40~50만, 히든도어 70~90만 원이다 [S41]. 업체 자료는 히든도어 1짝 140~180만 원(기본형)이다 [S40]. 히든도어는 문과 벽 단차 2mm 이내, 도어 두께 35T 이상, 히든 경첩이 필요하다. 벽을 도배·필름으로 마감하면 래핑도어, 도장이면 백골도어를 쓴다 [S39][S40].
7. **친환경 인증은 HB(한국공기청정협회)만 등급 기준을 공개한다.** 일반자재 최우수는 TVOC 0.10, HCHO 0.008 mg/㎡·h 미만이다. HB 인증을 받으면 환경부 사전적합확인이 면제되고 '실내마크'를 반드시 붙여야 한다 [S27]. LX 제품 페이지에는 HB 대신 환경표지·EPD·실내표지만 표시되어 있다 [S05][S16][S18]. 벽지 KS 인증은 확인하지 못했다.
8. **제조사 데이터는 사실 메타데이터만 쓸 수 있다.** LX는 규격·구조·인증을 공개하지만 가격은 공개하지 않는다(상담 안내) [S05]. 신한벽지 약관은 사전승낙 없는 정보 복제·제공을 금지한다 [S24]. 제조사 원문이나 이미지를 RAG에 그대로 넣으면 안 되고, 수치는 구조화하고 설명은 자체 요약으로 쓰는 편이 안전하다.
9. **시각화(3주 판단)**: 국내 제조사 중에는 신한벽지 '셀프코디'(샘플 방 4종 배경) 정도만 있다 [S23]. LX 사이트에는 시뮬레이터가 없다 [S01]. 해외 AI 도구는 '선택한 벽면만 교체' 방식이 주류지만 패턴 스케일·색 정확도는 보장하지 않는다 [S62][S63]. 학생 팀 3주라면 **샘플 방 사진 + 사전 마스크 레이어 + 텍스처 교체(결정론)** 방식이 현실적이다. 사용자 사진에 세그멘테이션(SAM 계열)을 붙이는 기능은 데모 수준이 한계다.
10. **'호텔 같은', '몰딩 없는' 같은 고객 표현은 대부분 목공·전기 추가로 이어진다.** 표현 사전에서는 '스타일 → 옵션 후보 + 되묻기 질문 + 연계 공정 플래그' 3종을 함께 저장해야 한다. 예를 들어 견적 범위 밖인 전기·벽체 목공이 끌려오면 그 사실을 안내해야 한다(§6, §7).

### 1.4 색·패턴과 무늬 맞춤 로스

**무늬 맞춤 유형** [S68][S69][업계-해외]

| 유형 | 정의 | 로스(참고) |
|---|---|---|
| Random/Free | 이음에서 무늬를 맞출 필요 없음 | 약 5~8% |
| Straight | 모든 폭이 같은 높이에서 무늬가 맞음 | 약 10~15% |
| Half-drop | 폭마다 리피트의 절반씩 어긋나며, 대각선 흐름 | 약 15~20% 또는 20~30% → **상충** |
| Multiple drop | 4폭 이상이 지나야 반복됨 | 미확인(드롭보다 큼) |

- 국내 설명: 무늬를 맞추려면 잘라내는 부분이 생겨 실제 시공 면적이 줄어든다. 리피트 간격과 벽 높이에 따라 한 롤에서 나오는 폭 수가 달라진다. 산업인력공단 시험 안내도 무늬지는 상하 구분을 먼저 정하라고 한다 [S37][기사, 2026-09-24].
- **여분 정책 (상충)**: LX는 손상·패턴 맞춤용으로 1~2롤 추가 주문을 권한다 [S08][공식]. 숨고는 절단 손실과 패턴 여유로 5%를 잡는다 [S34][업계]. 실무 자료는 10~15%를 권한다 [S74][업계]. 해외 계산기는 퍼센트 대신 1~3폭을 추가하라고 한다(재단 길이에 이미 맞춤 로스가 들어 있어 이중 계산이 된다는 이유) [S69][업계-해외]. → **팀 정책 1개를 고르고 근거를 저장**한다.
- **로트(LOT) 관리**: 생산일자·LOT 번호를 확인한다 [S33][커뮤니티, 2006]. 같은 패턴은 한 로트로 발주한다 [추정].

**결정론적 계산식 제안** (계산 엔진용. LLM은 결과를 설명만 한다)

```text
면적법(무지·랜덤, LX식)   롤 수 = ceil( 시공면적㎡ ÷ 롤면적㎡ )                         [S09]
폭수법(패턴, 권장)        필요 폭 수   = ceil( 벽 둘레(창·문 제외 전) ÷ 롤 폭 )
                          재단 길이    = 벽 높이 + 재단 여유
                                         (여유 ≈100mm [S08] / 상하 약 5cm [S33] / 위아래 약 10cm [S36] → 상충, 팀 기준 필요)
                          (무늬 있음)  재단 길이 = ceil(재단 길이 ÷ 리피트) × 리피트            [S69]
                          (하프드롭)   위 값 + 리피트/2 (홀·짝 폭 교대)                        [S68][추정: 단순화]
                          롤당 폭 수   = floor( 롤 길이 ÷ 재단 길이 )
                          롤 수        = ceil( 필요 폭 수 ÷ 롤당 폭 수 ) + 여분(팀 정책)
```

- **계산 예시(조사원 계산, 가상 값)**: 방 둘레 16.5m, 벽 높이 2.4m, 여유 0.1m, 실크 1.06m×15.6m.
  - 무지: 필요 폭 16, 재단 길이 2.5m, 롤당 6폭 → **3롤**.
  - 리피트 0.53m straight: 재단 길이 ceil(2.5÷0.53)=5 → 2.65m, 롤당 5폭 → **4롤**(+33%). 패턴 하나로 롤 수가 한 단계 뛴다는 것을 고객에게 보여 줄 수 있다.

## 3. 시공 '레시피' 지식 구조 설계 (조사 질문 3)

### 3.1 설계 원칙

1. **선택 단위(option)와 공법(recipe)을 분리**한다. 고객은 '실크·회벽·크림'을 고르고, 엔진은 그 선택에 맞는 레시피(실크 표준: 철거 + 퍼티 + 띄움 초배 + 맞댐)를 붙인다. 같은 옵션도 현장 조건(기존 합지 여부, 구축 여부)에 따라 레시피가 바뀐다 → `recipe.preconditions`.
2. **수치는 전부 테이블 값**으로 저장한다(롤 폭, 로스율, 대기시간, 인·일). 각 값에는 `source_ids`를 붙인다. 출처 간 값이 다르면 범위(min/max)와 `policy_value`(팀 기준값)를 함께 저장한다. LLM은 이 값을 읽어 **설명만** 한다.
3. **공정 의존성은 엣지 테이블(dependency)** 로 둔다. PostgreSQL 재귀 CTE로 선행·후행 체인과 일정 영향을 계산하므로 그래프 DB는 필요 없다.
4. **변경 규칙(change_rule)** 은 '트리거 → 효과(jsonb)' 형식으로 저장한다. 엔진은 효과의 파라미터만 적용하고, 설명 문구는 RAG 청크로 생성한다.
5. **RAG(pgvector)에는 설명 텍스트만** 넣는다. 옵션·레시피·하자·규칙을 자체 요약한 문장과 출처 요약을 청크로 만든다. 제조사 원문은 이용조건을 확인한 뒤에만 적재한다(§4.3).

### 3.2 엔티티 관계 (요약)

```text
source ─┬─< material >── texture
        │       │
        │   option_item ──< recipe ──< recipe_step >── (tools, consumables)
        │       │              │             │
        │       │              └──< inspection_point
        │       └──< expression_lexicon(maps_to)
        ├─< dependency (trade|recipe|step → trade|recipe|step, lag, condition)
        ├─< defect (related options/steps)
        ├─< change_rule (trigger → effects)
        └─< kb_chunk (embedding vector, entity_type/ref)
trade(공정) ── 모든 엔티티의 분류 축 (WALLPAPER, CARPENTRY, FILM, PAINT, FLOOR, ELEC1, ELEC2 …)
```

**질의 예시 1: 도배의 모든 선행 공정 체인(재귀 CTE)**

```sql
WITH RECURSIVE chain AS (
  SELECT d.from_ref, d.to_ref, d.min_lag_h, 1 AS depth
  FROM dependency d
  WHERE d.to_kind = 'trade' AND d.to_ref = 'WALLPAPER'
  UNION ALL
  SELECT d.from_ref, d.to_ref, d.min_lag_h, c.depth + 1
  FROM dependency d JOIN chain c ON d.to_ref = c.from_ref
  WHERE c.depth < 10
)
SELECT * FROM chain ORDER BY depth;
```

**질의 예시 2: 옵션 변경 시 적용할 규칙**

```sql
SELECT rule_id, effects, explain_ko, source_ids
FROM change_rule
WHERE trigger->>'group' = 'ceiling_molding'
  AND (trigger->>'to') IN ('CP_MOLD_NONE', '*')
  AND (trigger->>'from') IN ('CP_MOLD_FLAT', '*');
```

### 3.6 다른 공정(필름·도장·바닥)으로 넓히는 방법

같은 테이블에 `trade` 한 줄과 레시피·단계·의존성만 추가하면 된다.

| 공정 | 레시피 단계(요약) | 선행/후행 의존성 | 검수·하자 | 근거 |
|---|---|---|---|---|
| **필름(FILM)** | 표면 청소 → 찍힘·틈 퍼티 → 샌딩 → (흡수성 목재·MDF) 프라이머 → 건조 → 여유 두고 재단·기준점 부착 → 헤라로 기포 제거 → 코너·끝 열압착 | 필름 → 도배(FS) [S11] | 기포·이물질, 코너 커팅 [S11]. 습기·고열 부위 수축·변색 [S46] | [S46][S06][S11] |
| **도장(PAINT)** | 마스킹·커버링 → (짙은 색) 젯소 2~3회 → 붓 테두리 → 롤러 면 → 건조 후 2회 덧칠 | 도장 → 도배(FS) [S11] | 도포 균일성, 튐·오염, 퍼티 상태. 덜 마른 상태에서 오염(겨울 건조 지연) | [S06][S11] |
| **바닥(FLOOR, 마루)** | 선행 점검: 바닥 습도 5% 미만, 미장 보수, 먼지·기름 제거, 난방 배관 통수 시험 → 시공 → 벽체·문틀·붙박이장과 약 1cm 간격 | 마루 → 도배, 도배 → 장판 [S11]. 바닥 → 걸레받이 | 들뜸(요철·균열 보수 부실), 벌어짐, 변형(습도) [S21]. 수평, 걸레받이 실리콘 [S11] | [S21][S11] |

**공정 추가 체크리스트**: ① `trade` 등록 → ② `material`(규격·인증) → ③ `option_item` → ④ `recipe` + `recipe_step`(qty_basis·labor·wait) → ⑤ 기존 DAG와 `dependency` 연결 → ⑥ `inspection_point`·`defect` → ⑦ `change_rule` → ⑧ `expression_lexicon` → ⑨ `kb_chunk` 생성·임베딩.

### 3.7 그래프 DB가 필요해지는 시점

- 현재 규모(공정 10여 개, 엣지 수백 개 이하)에서는 재귀 CTE로 충분하다.
- '조건부 다단계 영향(3단계 이상) 탐색'이나 '비슷한 옵션 추천' 질의가 많아지면, PostgreSQL 확장인 Apache AGE(openCypher)를 검토할 수 있다. 다만 이것도 **새 의존성이므로 팀 논의가 필요**하다. 이번 조사에서 AGE 자체는 웹으로 확인하지 않았다(조사원 사전지식).

## 8. 에이전트 설계 시사점

1. **'옵션 = 자재 등급 × 질감 × 색·패턴 × 레시피'의 4축으로 정규화**한다. LLM은 표현 → 옵션 후보 매핑까지만 맡는다. `confidence`가 낮거나 목공·전기가 끌려오는 경우(#2·#3·#16 등)에는 반드시 되묻는다. 확정된 옵션 코드만 계산 엔진에 넘긴다.
2. **상충 값은 범위로 저장하고 팀 기준값 1개를 명시**한다(로스율, 비용, 생산성). 설명할 때는 "자료마다 ○~○로 다르며 믿집은 ○를 씁니다"처럼 근거와 함께 말하게 한다. 같은 페이지 안의 불일치(S35 FAQ, S36 천장 비중)는 데이터 품질 플래그로 남긴다.
3. **공식 공정표(S11)를 의존성 DAG의 뼈대로** 쓰고, 업계 값(목공 후 24h 등)은 `confidence=medium`으로 덧붙인다. 옵션 변경 → `change_rule` → 의존성 재계산(재귀 CTE) → 일정 차이를 결정론적으로 보여 줄 수 있다. 그래프 DB 없이 3주 안에 구현할 수 있다.
4. **RAG는 '자체 요약 + 출처 링크'만** 적재한다. 제조사는 약관상 원문·이미지 전재 위험이 있으므로 규격·인증 수치만 구조화하고, 가격은 TTL을 붙인 스냅샷으로 둔다. HB 기준표·LX 공정 체크리스트처럼 신뢰도 높은 원천을 우선한다.
5. **견적 범위 밖 공정 플래그(`in_quote_scope=false`)** 를 옵션과 규칙에 넣는다. 그러면 '간접조명 → 전기', '마이너스 걸레받이 → 벽체 목공', '필름 리폼'을 안내만 하고 금액은 산출하지 않는 일관된 UX를 만들 수 있다. 시각화는 Level A(샘플 방 + 레이어)로 시작해 결과마다 '참고 이미지'라고 고지한다.
