# RAG 검색 평가

상담 근거 검색이 질문에 맞는 조각을 위쪽에 가져오는지 잰다. LLM 호출 없음(무료).

## 파일
- `questions.jsonl`: 평가 질문 90개 (도배 33 · 목공 33 · 공통 24, dev 60 · held-out 30)
- `questions_300.jsonl`: 실제 고객 질문을 바꿔 쓴 300개 (도배 115 · 목공 85 · 공통 100, dev 200 · held-out 100). `expect`: answer 230 · no_source 51 · engine 19(계산 엔진 몫, 검색으로 재지 않음). 출처 · 만든 법은 `d10-/reports/데이터셋 조사/2. 질문 세트 300.md`
  - `expect`: `answer` | `no_source`(가격 · 업체 추천 · 범위 밖처럼 자료로 답하면 안 되거나 자료가 없는 질문)
  - `gold`: 정답 조각 `{ref, grade, why}`. grade 2 = 직접 답, 1 = 부분 관련. 후보(여러 검색의 상위 15개 합집합) + 말뭉치 낱말 검색으로 사람 대신 판정해 넣었다
  - `from`: 질문 출처 (`book` 시공 안내서, `mokgong_qa:q-…` 팀 목공 고객 질문, `written` 직접 씀)
- `corpus.py`: 서버 적재용 CSV로 합친 말뭉치 만들기 (화면 자료 `data/consult` K1~ · 팀 자료 `data/processed` K2001~ · 로컬 추가 자료 `data/local`(git 제외) K5001~). 번호 규칙은 서버와 같은 `backend/app/knowledge/sources.py`. 결과는 `.cache/`(git 제외)
- `rank.mjs`: 화면 검색(`rag.ts`)으로 질문마다 순위 뽑기
- `rank_server.py`: 서버 검색(`backend/app/knowledge/bm25.py`)으로 질문마다 순위 뽑기 (DB 없이, 의미 검색 없이)
- `dense.py`: 질문 임베딩 → DB(pgvector)에서 의미 검색 순위 (`.cache/dense.json`, 유료: 질문 90개 약 2천 토큰)
- `hybrid.py`: 키워드 + 의미 검색 합치기 무게를 dev로 고르고(`--final`로 held-out 한 번) 확인
- `metrics.py`: hit@1 · hit@5 · recall@5 · MRR · nDCG@5, 자료 없음 질문의 '자료 부족' 판단률

## 돌리기
```bash
python evaluation/rag/corpus.py
node evaluation/rag/rank.mjs --name current
python evaluation/rag/rank_server.py --name server
python evaluation/rag/metrics.py evaluation/rag/.cache/rank_current.json evaluation/rag/.cache/rank_server.json
```
- 화면 자료 CSV 다시 만들기: `cd backend && uv run python -m app.knowledge.json_csv ../frontend/public/v2/rag5.json ../data/consult/consult_knowledge_rag.csv`
- held-out은 마지막에 한 번만: `--final`
- 로컬 추가 자료(책)가 없으면 K5001~ 정답은 찾을 수 없어 점수가 낮게 나온다. 책 조각이 있는 로컬에서 잰다

## 4단계: 키워드 + 의미 검색 (2026-11-13)
- 조각 임베딩: text-embedding-3-small 1536차원, 2,154조각 (75만 토큰, 약 0.015달러)
- 고른 무게(`bm25.CONF`): 의미 검색 `dense_w` 0.75(위 30개), 같은 공정 조각 `trade_w` 0.012. 공정 자리 확보는 뺐다 (무게만으로 같은 결과)
- dev 격자: 의미 검색 0.5~1.0 × 공정 0.008~0.016이 모두 hit@5 0.72~0.76이라 가운데를 골랐다

| 검색 | 나눔 | hit@1 | hit@5 | recall@5 | MRR | nDCG@5 |
|---|---|---|---|---|---|---|
| 키워드만 (자리 확보, 3단계까지) | dev | 0.414 | 0.603 | 0.304 | 0.669 | 0.398 |
| 키워드 + 의미 + 공정 무게 | dev | 0.362 | 0.741 | 0.321 | 0.686 | 0.421 |
| 키워드만 (자리 확보, 3단계까지) | held-out | 0.296 | 0.593 | 0.256 | 0.599 | 0.366 |
| 키워드 + 의미 + 공정 무게 | held-out | 0.407 | 0.741 | 0.319 | 0.647 | 0.459 |
- 공정별 hit@5 (held-out): 도배 0.600 → 0.800, 목공 0.400 → 0.500, 공통 0.857 → 1.000
- dev hit@1은 내려갔다 (0.414 → 0.362). 상담은 위 6개를 함께 넘기므로 hit@5를 우선했다
- held-out은 이 설정으로 한 번만 봤다. 다음 무게 조정은 질문 세트를 늘린 뒤 새 held-out으로 본다

## 질문 300 정답 판정과 무게 다시 고르기 (2026-11-13)
- 정답(gold)은 '자료로 답함' 230개에만 붙였다. 후보 = 키워드만 · 의미 검색만 · 합친 검색의 위 12개 합집합(질문당 평균 24개), 번호 순으로 섞어 판정(사람 대신 Claude 서브에이전트, 기준은 90문항과 같음). 정답 조각 1,025개
- 자료 빈칸: 230개 중 직접 답하는 조각(grade 2)이 있는 질문은 138개(60%). 부분 근거만 83개, 근거 없음 9개 (운영 방식 · 개인정보 · 실측 비용 · 자격 확인 · 유치권 · 문 열림 방향 등)
- 90문항으로 고른 공정 무게(0.012)는 새 질문에서 손해였다(dev hit@5: 공정 무게 없이 0.723 → 0.682). 두 세트 dev 208문항으로 다시 골라 `trade_w` 0.002로 낮췄다
- 새 held-out 100(답 있는 73문항, 한 번만 봄)

| 검색 | hit@1 | hit@5 | recall@5 | MRR | nDCG@5 |
|---|---|---|---|---|---|
| 키워드만 | 0.479 | 0.685 | 0.398 | 0.676 | 0.466 |
| 의미 0.75 · 공정 0.012 (4단계) | 0.342 | 0.699 | 0.392 | 0.651 | 0.433 |
| 의미 0.75 · 공정 0.002 (지금) | 0.356 | 0.726 | 0.420 | 0.669 | 0.458 |
- hit@1은 키워드만보다 크게 낮다(의미 검색이 부분 근거 조각을 맨 위로 올림). 위 6개를 함께 넘기므로 hit@5 · recall을 우선했고, 맨 위 정확도는 재순위(선택 단계)로 다룬다
- 판정은 사람이 아니라서 표본을 사람이 확인해야 한다
