# 에이전트 평가

기준은 하나다: **고객에게 필요한 정보만, 쉽게**. 에이전트마다 사례 약 5,000개를 만들고, 코드 채점은 전부에, 판정 LLM은 층화 표본에만 쓴다.
CI에서 유료 호출은 0회다 (AGENTS.md 4장). 유료 실행은 단계마다 금액을 먼저 보이고 승인받은 뒤에만 한다.

| 폴더 · 파일 | 하는 일 |
| --- | --- |
| `dobae/` | 도배 상담 비교 평가 ('Claude에게 그냥 묻기' vs 믿집 상담, 사례 15개) |
| `common/` | 생성기 공통 도구, 사례 형식 문서, 계산 엔진 어댑터, 비용 계산 |
| `wallpaper/` · `carpentry/` | 공정 의견 사례 생성기(4,995개씩)와 표본 100개 |
| `scorers/` | 코드 채점 규칙 · 어려운 용어 표 · 모범 답 |
| `judge/` | 판정 LLM 기준표(`rubric_v1.md`)와 판정 스키마 |
| `run_agent.py` | 공통 실행기 (기본은 호출 수 · 예상 비용만) |
| `check_cases.py` | 무료 점검 T0 |
| `tests/` | 단위 테스트 (DB · Redis · LLM 없이) |

## 단계

| 단계 | 내용 | 비용 |
| --- | --- | --- |
| T0 | 사례 생성 · 계산 엔진 다시 돌리기 · 규칙 모순 점검 · 단위 테스트 · 가짜 LLM으로 실행기 경로 | 무료 |
| T1 | 공정마다 dev 20개로 실제 토큰 · 비용을 잰다 | 승인 후 |
| T2 | 프롬프트를 바꿀 때 150개 | 승인 후 |
| T3 | 전체 5,000개를 Batch로 | 승인 후, `llm.py`에 Batch가 생긴 뒤 |

```bash
cd backend
uv run python ../evaluation/wallpaper/make_cases.py      # 4,995개 + 표본 100 (약 1초)
uv run python ../evaluation/carpentry/make_cases.py      # (약 2초)
uv run python ../evaluation/check_cases.py               # T0 점검 (두 공정 9,990개, 약 16초)
uv run pytest ../evaluation/tests                        # T0 단위 테스트 (약 10초)

uv run python ../evaluation/run_agent.py --agent wallpaper --split dev --sample 20 --judge 9           # 호출 수 · 예상 비용만
uv run python ../evaluation/run_agent.py --agent wallpaper --split dev --sample 20 --judge 9 --fake    # 가짜 LLM (무료)
uv run python ../evaluation/run_agent.py --agent wallpaper --split dev --sample 20 --judge 9 --live    # T1 (유료, 승인 후)
uv run python ../evaluation/run_agent.py --agent wallpaper --rescore ../evaluation/wallpaper/results/<폴더>   # 다시 채점만
```

- `--sample N`은 `--stratify` 키(기본 `category`)의 층마다 고르게 뽑는다. 두 나눔을 같이 뽑으면 dev:held-out 2:1을 지킨다.
- 프롬프트를 고칠 때는 dev만 보고, held-out은 마지막 확인에만 쓴다.
- 실행기는 `.env`에서 `ANTHROPIC_API_KEY` · `LLM_MODEL` · `LLM_EFFORT`만 읽는다. 모델을 바꿔 재려면 `LLM_MODEL`을 바꾼다.
- `--batch`는 자리만 있다. `llm.py`에 Batch 호출이 생기면 `run_agent.run_batch`에 붙인다.

## 실행 흐름

```
사례(input) → common/trades.py: 계산 엔진 견적 + 입력 글(card_text)
           → app.agent.<wallpaper|carpentry>.plan(card_text, 견적)   ← llm.parse를 감싸 원문 · 사용량 기록
           → scorers/trade_plan.score(원문, 사례 expect)               ← 코드 채점 (전부)
           → judge/judge.py (층화 표본만, 화면에 보이는 의견)          ← 판정 LLM
           → <agent>/results/<날짜-시각>/raw.json · summary.md
```

`common/trades.py`의 입력 글은 상담 코드(`consult/service.py`의 `card_text` · `mokgong_text`)에서 옮긴 것이다. 공정 플러그인(TradeSpec)이 생기면 이 파일만 TradeSpec을 부르도록 바꾼다.

## 코드 채점 (사례 전부)

`scorers/trade_plan.py`. 모델이 쓴 원문(코드 검사로 버리기 전) 기준이다.

| 검사 | 기준 |
| --- | --- |
| `no_digits` | 요약 · 단계 · 실측 질문 · 주의 어디에도 숫자(0~9)가 없다 |
| `no_number_words` | 말로 쓴 금액 · 기간 · 인원이 없다 ('십만 원', '하루 정도 걸려요', '두 명') |
| `step_keys` | 단계 키가 계산 엔진 공정표 안에 있고 겹치지 않는다 |
| `step_cover` | 공정표 단계마다 하나씩 있다 |
| `summary_len` · `summary_sent` | 요약 20~200자, 1~2문장 (프롬프트는 두 문장) |
| `item_len` | 단계 · 실측 질문 120자, 주의 160자 이하 (코드 검사 한도는 200 · 300자) |
| `visit_count` · `caution_count` | 실측 질문 3~6개, 주의 2~4개 |
| `caution_source` | 주의 출처가 지식 파일 '출처' 목록 안에 있다 |
| `style` | '-해요'체 (…다 · …음 · …함으로 끝나지 않는다) |
| `terms` | 어려운 용어는 처음 나온 문장에서 쉬운 말로 풀었다 |
| `must` · `must_not` | 사례의 기대 검사 규칙 (아래) |

기대 검사 규칙 (사례마다 `expect.must` · `must_not`, 키워드는 `RULES`):

| 규칙 | 뜻 | 보는 곳 |
| --- | --- | --- |
| `sum.*` | 요약에 드러낼 것. 도배: 등급 · 천장 포함 여부 · 사는 집인지. 목공: 고른 항목 · 문틀까지인지 · 사는 집인지 | 요약 |
| `prep.mention` | 사는 집이면 짐 · 가구 · 보양 | 전체 |
| `after.<줄 키>` | '실측 후' 줄(철거 · 폐기물 · 짐 이동)마다 왜 실측 뒤인지 | 실측 질문 · 주의 |
| `order.other` | 같이 하는 공정이 있으면 목공이 먼저라는 순서 | 같은 문장에 공정 이름 + 순서 말 |
| `check.<칸>` | '모르겠어요'로 기본값을 쓴 칸을 실측 때 확인 | 실측 질문 · 주의 |
| `balcony.check` | 도배 · 발코니 확장이면 결로 · 곰팡이 확인 | 전체 |
| `not_chosen.<항목>` | 고르지 않은 항목(도배 천장, 목공 4항목) 언급 | '안 함 · 빼요 · 따로 하는 공사' 문장은 괜찮다 |
| `empty.moving` | 빈집인데 짐 이야기 ('짐 정리 없이 바로…'도 필요 없는 말) | 전체 |
| `other.trade` | 같이 하지 않는 공정 언급 | '안 함' 문장은 괜찮다 |
| `balcony.none` · `balcony.any` | 도배 · 발코니 확장이 아닌데 발코니 / 목공(지식에 없음) 발코니 | 전체 |
| `scope` | 범위 밖 공사 (욕실 · 타일 · 장판 · 마루 · 전기 배선 · 콘센트 · 창호 · 중문 · 가벽 등) | '따로 하는 공사' 문장은 괜찮다 |

어려운 용어 표 (`scorers/terms.py`): 초배 · 정배 · 퍼티 · 샌딩 · 덧방 · 보양 · 소요량 · 문선 · 천장틀 · 품셈 등 기준 이름, 목공의 할증(버리는 몫).
같은 문장 안에 쉬운 풀이(예: '밑종이를 먼저 바르고(초배)')가 있으면 통과다. 흔히 쓰는 말(등박스 · 우물천장 · 무몰딩, '품이 든다', 도배의 '짐 있는 집 할증')은 넣지 않았다.

`scorers/witness.py`는 규칙을 모두 지키는 모범 답이다. T0에서 사례마다 이 답이 모든 검사를 통과하면 규칙끼리 모순이 없다는 증거이고, `--fake` 실행의 가짜 LLM 응답으로 쓴다.

## 판정 LLM (층화 표본만)

`judge/rubric_v1.md` + 그 공정의 지식(SKILL.md)이 시스템 프롬프트다 (공정마다 같아 캐시된다). 화면에 보이는 의견(버린 항목을 뺀 것)을 본다.

| 기준 | 뜻 |
| --- | --- |
| `necessary_only` 필요한 정보만 | 이 집 조건에 맞는 말만, 핵심(실측 후 줄 · 모르는 칸 확인)은 빠짐없이 |
| `plain_words` 쉬운 말 | 업계 말을 안 쓰거나 풀어 씀, 짧은 '-해요'체 |
| `actionable` 할 일이 분명함 | 실측 때 무엇을 묻고 확인할지 바로 앎 |
| `correct` 틀린 내용 없음 | 입력 · 지식과 어긋나지 않고, 단정 · 업체 탓이 없음 |

기준마다 1~5점 정수와 이유 한 줄. 점수 범위는 코드에서 본다. 호출은 `app.agent.llm.parse`(effort 기본 low)이고, 모델은 지금 `LLM_MODEL` 하나를 같이 쓴다.

## 결과 파일

- `raw.json`: `{"meta": {agent, model, effort, prompt_version, rubric, cases, split, sample, stratify, seed, judge, started}, "results": [...]}`
  - 결과 하나: `id · split · category · status(ok · failed) · reason · raw(모델 원문) · shown(화면 의견) · dropped · usage · scores{checks, rules, detail}` (+ `judge` · `judge_usage` · `judge_error`)
- `summary.md`: 검사별 통과율(전체 · dev · held-out), 규칙별, 판정 평균, 범주별, 비용 · 시간, 실패 예
- 가짜 LLM 결과(`*-fake`)와 전체 사례(`cases_5k.jsonl`)는 커밋하지 않는다 (`.gitignore`)

## 지난 실측 의견에 코드 채점을 돌려 본 결과 (무료)

`dobae/results`의 세 실행(Opus 5.5 · `wallpaper-v1`)에서 나온 도배 공정 의견 135개를 지금 채점기로 다시 매겼다. 판정 LLM은 돌리지 않았다.

| 검사 | 통과 |
| --- | ---: |
| 숫자 · 말로 쓴 숫자 · 단계 키 · 단계 빠짐 · 길이 · 개수 · 말투 | 100% |
| 요약 1~2문장 | 99% (134/135) |
| 꼭 언급 | 99% (134/135, 사는 집인데 요약에 안 드러남 1) |
| 언급하면 안 됨 | 63% (85/135): 빈집 의견 90개 중 50개가 '빈집이라 짐 정리 없이 바로…'처럼 짐 이야기 |
| 어려운 용어 풀이 | 0% (0/135): 초배 135 · 정배 131 · 덧방 49 · 보양 47 · 퍼티 29 · 샌딩 17번을 풀지 않고 씀 |

- 실측 질문은 135개 모두 6개, 주의는 모두 4개로 늘 상한을 채웠다.
- 다음 프롬프트(`wallpaper-v2`)에서 다룰 것: 용어 풀이, 빈집 짐 이야기 빼기, 개수 줄이기. 계산 엔진 단계 이름 '초배 · 정배'도 화면에 그대로 보인다.

## 한계

- 키워드 채점은 거칠다. '안 함' 맥락은 같은 문장의 '않 · 안 해 · 빼 · 제외 · 없이 · 빠져 · 따로 하는 공사' 같은 말로만 본다. 뉘앙스는 판정 LLM으로 본다.
- 도배 입력은 숫자를 빼면 432가지라 4,995개는 구조마다 약 11~12번 반복이다 (`wallpaper/README.md`). 목공은 공간 이름 덕분에 4,527가지다.
- 판정 모델을 따로 고를 수 없다 (`llm.parse`에 모델 인자가 없음). 역할별 모델이 생기면 판정 역할로 바꾼다.
- 토큰 추정은 도배만 실측이다. 목공 · 판정 · Sonnet · Haiku는 T1에서 다시 잰다.
