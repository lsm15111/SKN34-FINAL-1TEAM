# 요청 점검 부탁 뽑기 평가

`app.assistant.asks.extract`가 고객 말에서 수 · 값 · 보일 카드를 맞게 뽑는지 재요. 무료(LLM 없음). 설계는 `docs/v4/11-request-check.md`.

## 파일
- `asks_set.jsonl`: 120줄. v4 비서 대화의 고객 말 118줄(QA DB · 보기용 DB, 카드 단추 글 빼고 중복 없이) + QA 보고서의 고객 말 2줄.
  - 정답 칸: `count`(찾거나 골라 달라는 수, 이름을 댄 업체 수는 아님) · `price`(액수 · 차이를 묻는 말, 포함 여부만 묻는 말은 아님) · `show`(보여 달라 · 바꾸겠다는 카드 종류). 어느 카드인지 모르는 줄은 `show: null`(카드 채점에서 뺌).
  - `split`: dev 80 · held_out 40(seed 20261123).
- `score_asks.py`: 정밀도 · 재현율. `cd backend && uv run python ../evaluation/v4/request_check/score_asks.py --split all --show-misses`

- 한계: 이 120줄을 보며 규칙을 정하고 고쳤어요(dev · held_out 모두). 그래서 held_out도 처음 보는 말이 아니고 점수가 실제보다 좋게 나와요. 새 QA 차수의 고객 말로 다시 재야 해요.
- 턴 전체(점검 글로 카드를 보였는지)는 대본 시험(`backend/tests/test_v4_request_check.py`)과 아래 실측으로 봤어요.

## 실측(2026-11-23, OpenAI 길 gpt-6.1-terra, 유료)
- `live_turns.py`: 고객이 실제로 한 말 15개(카드 부탁 8 · 조사 부탁 4 · 앞 대화가 있는 카드 부탁 3)를 한 말씩 새 공사에 보내 채웠는지 봐요. 고치기 전은 `5a2f6d3`(feat-v4-secretary) 그대로인 임시 작업 폴더, 고친 뒤는 이 갈래예요. 평가 DB `mitjip_eval_reqcheck` · Redis 11.

- 읽는 법
  - 이 말들은 고치기 전 코드도 다 채웠어요(오늘 아침 고친 get_home 설명 136ffc0 포함). 턴 끝 점검 글은 한 번도 나서지 않았어요(trace.asks.retry 모두 false). 그래서 이 표로는 점검의 효과를 보이지 못해요. 점검은 모델이 놓칠 때의 안전망이고, 실제로 얼마나 놓치는지는 trace.asks(unmet · retry)로 앞으로 세요.
  - 첫 말투('채우지 못하는 것은 못 한다고 말해요')는 비서를 일찍 멈추게 했어요(r1). '되묻지 말고 도구로 끝까지, 한 길로 모자라면 다른 도구로'로 바꾼 뒤 r1 · r2 3/3씩이에요.
  - '이번 부탁' 줄은 턴 비용을 조금 늘려요(같은 말 h1 $0.0020 → $0.0021).
  - 한 번 ~ 두 번만 돌린 판이라 흔들림 폭은 몰라요.
